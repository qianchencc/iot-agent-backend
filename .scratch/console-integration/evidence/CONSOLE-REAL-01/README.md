日期：2026-11-05。入口 `http://127.0.0.1:5185`，Java3381／Node3382；真实Chrome、真实管理登录。没有使用API200或单测代替前端操作结果。

## 结论与根因

此前完整指令工作只验证10项文本保存、重读、组装及旧轮次快照，不能外推为整个控制台或全部配置的业务验收。本轮确认了三个实质错位：

- 初始实际Java包是旧冻结包：审计仅有列表接口，名单仍收园区／身份域／主体元组；界面已使用tenants/members/events/detail和手机号＋可选备注的新契约。Vite实际代理正确指向Java；`Route GET:...not found`的JSON也由Java错误处理器生成，不足以判定请求落到Node。工作区源码存在不等于进程已运行它。
- 初始Node从部署环境中的已有连接初始化Langfuse，却不在health报告观测采用；Java加密配置中的保存值为关闭／未配置。二者权威来源不同，不能把控制台状态当成SDK状态。缺少报告也不能被标为无法连接，本轮补充了该判断与失败先行回归。
- 原全局“下一轮生效”、测试模型“当前草稿参数”等说法超出了实现：扫描按周期读取，观测需重启，连接测试只是固定1 token最小请求并丢弃响应正文。

期间另一个线程发布了完整 `var/fixed-latest-20261105-181818` Java／Node，包含新名单、审计、观测桥接和动态设置读取。保留该完整部署，没有用本轮旧基线隔离构建或局部旧class覆盖它，也没有回滚其他线程的新schema。由于新Node采用Java保存的关闭值，原有Langfuse一度实际关闭；本轮经真实控制台普通保存，将原有连接安全存入Java加密配置并启用，确认空闲后按固定入口重启同一完整发布包，去掉Node重复的3项旧启动凭据。没有更换SDK、模型或10项指令。
