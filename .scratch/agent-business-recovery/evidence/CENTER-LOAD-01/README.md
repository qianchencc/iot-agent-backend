2026-11-04。微信开发者工具当前真实账号验收通过；真机未验收。只验证读取与刷新，不创建任务、不下发设备控制、不发送通知。

## 问题与修复

任务与通知虽已存于 Java/MySQL，普通读取仍先调用 `TaskFacade.scope()`，同步等待整份公司授权目录。Company 目录为保持控制绑定实时性，只合并在途请求，不复用已完成结果；因此只有两条本地记录也要等待数秒。真实线程采样停在 `TaskFacade.scope → IotAdapter.loadAuthorizedDeviceScope → Mono.block`，尚未进入本地查询。

本轮将只读授权元数据纳入既有 `ReadSnapshots`，不另建缓存体系，也不缓存任务、通知结果：

- 普通 HTTP 读取只消费后端已持有的授权读模型；冷启动返回 `503 TASK_READ_PREPARING`，前端既有准备协议继续读取，不把准备中当空列表。
- 目录沿用 CURRENT 策略后台更新。更新中可使用最近一次成功范围；更新失败后关闭读取，明确 401/403 通过共享凭据屏障立即废止已持有范围。身份、租户、来源和主体仍隔离。
- 任务与通知事实逐次读取本地库，不因授权读模型复用而延后新任务结果。确认、取消、恢复及控制绑定仍实时核权；已读回执按原 Runtime 已确认设计与列表共用读目录。
- 后台摘要组合用 `loadScope`，阻塞工作移至 bounded elastic；普通列表保留原始已核验主体，不再重建为只含 token 的主体。
- 真实 JFR 与 MySQL 回归另发现：无时间上限被转换为 `9999-12-31T23:59:59Z`，在上海时区成为 10000 年，导致摘要查询失败。现在缺失的上下限不生成对应 SQL 条件。
