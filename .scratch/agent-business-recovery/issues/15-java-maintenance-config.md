# 15: Java 维护配置真正生效

**What to build:** Java 管理侧安全地保存与变更业务指令、模型选择、通用执行预算与限额；变更经校验、持久化（MySQL）后，活跃运行在下一次执行边界获得一致配置，不得在一轮执行中混用新旧配置；忙碌会话与重启有明确处理语义，失败不得返回“已接受”的假成功；Pi 会话与 MySQL 配置在重启后保持，不丢失已接受变更；维护操作有文档与审计；业务配置变更不需要改 Node，Node 源码与构建保持不变；私有 token、密钥与内部授权 ID 不出现在日志、事件、前端或错误信息中。

**Blocked by:** [01: Java 业务定义与通用 Node 执行引擎](01-java-business-generic-engine.md)

**Status:** ready-for-agent

## 本票必须自包含的规则

- Java 管理侧是业务指令、模型选择、通用预算/限额的唯一权威来源；不得在 Node 环境变量或前端硬编码第二份业务配置。
- 写入必须校验（类型、范围、权限、引用的模型/预算有效），持久化到 MySQL，并产生审计记录（谁、何时、旧值/新值摘要）；不得只改内存。
- 活跃运行采用一致的配置快照：一轮对话/任务执行内不混用新旧值；变更在明确的下一轮/下一阶段边界生效，并向操作者显示生效方式。
- 忙碌会话：明确返回“将在下一轮生效”或排队状态，不得静默丢弃；执行中的任务不得被中途改写到一半。
- 重启后配置与 Pi 会话从持久存储恢复；已接受的变更不丢、未接受的变更不假装存在。
- 失败（校验失败、存储失败、权限不足、并发冲突）必须返回明确错误和未生效状态；禁止先返回成功再后台失败。
- 业务配置变更不修改 Node 源码或构建；Node 仅消费 Java 提供的通用策略/数据。验证变更前后 Node diff 为空。
- 私有 token、密钥、内部授权键、供应商凭证不得出现在前端、事件、日志、错误或审计明文中；审计只存脱敏摘要。
- 本票不写生产配置；真实前端验收在隔离本地实例（独立 MySQL/配置）完成，明确标注本地范围。

## 验收条件

- [ ] 在隔离本地实例通过 Java 管理侧修改一条业务指令（如角色措辞/业务范围说明）与一个通用预算/限额，保存后 MySQL 与审计记录可核对，Node 目录 diff 为空、Node 构建未变。
- [ ] 真实前端发起新对话，观察到修改后的业务指令生效；旧配置不再影响新轮次，前端无需改动。
- [ ] 修改模型选择或限额后，新轮次按新值执行；达到限额时行为可观察且与配置一致，不出现半新半旧配置。
- [ ] 在会话/任务忙碌时提交变更，界面显示“下一轮生效/排队”或明确拒绝；执行中的轮次仍使用一致快照，不中途切换。
- [ ] 重启隔离实例后，已接受的配置、Pi 会话与审计仍在；未接受的失败变更不存在，不出现幽灵配置。
- [ ] 构造校验失败、存储失败、权限不足或并发冲突，返回明确错误且配置未变；不存在返回成功后实际未生效。
- [ ] 检查前端、事件、日志与错误输出，不含 token、密钥、供应商凭证或内部授权键；审计仅含脱敏摘要。
- [ ] 全程未写生产配置、未切换生产；证据含前后配置截图、审计、Node diff 说明、重启记录、脱敏诊断、构建/账号/来源/区域。

## 可追溯 Runtime 业务参考职责

对照 Runtime 的模型/指令配置、通用预算与维护边界，记录“Runtime 配置语义 → Java 配置/生效策略 → 前端与隔离证据”。Runtime 只读，不修改、不切换生产；不以修改 Runtime 配置迁就新后端。

## 工程回归与真实前端验收的区别

工程回归可验证配置持久化、快照一致性与失败语义；业务完成必须由真实前端观察到配置生效、忙碌处理与重启恢复，不以管理接口 200 或单测替代。

## 隔离与安全约束

业务修改只在隔离 worktree；原 backend 与 Runtime 只读，必要的真实前端修复另用独立 mp worktree且保持原契约。配置仅写隔离环境自有 MySQL；不读取生产配置或密钥明文、不写入或外传生产凭据。

## 证据要求

证据落在 `.scratch/agent-business-recovery/evidence/<CASE-ID>/`，含变更前后配置与审计、真实前端生效截图、忙碌/重启/失败场景、Node diff 与构建标识、脱敏诊断、账号/来源/区域。密钥类信息一律脱敏。

本票仅发布规格，尚未执行任何验收；不得以配置保存成功、接口 200 或单测通过宣称配置已生效。
