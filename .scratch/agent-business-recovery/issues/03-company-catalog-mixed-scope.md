# 03: 公司七类授权目录与照明+空调混合范围

**What to build:** 公司 Agent 依据当前真实 principal、tenant 与 source 读取覆盖七类设备的授权目录（环境、能耗、安全、空调、照明、门禁、视频），支持按名称/别名/位置检索与歧义澄清；对“关闭 26 楼各办公区的照明和空调，保留过道区域照明”这类混合范围，生成包含照明与空调的确认单，正确执行范围减法并列出拟执行、排除、已符合目标无需操作的台数，由服务端展开精确成员集合，按楼层与位置分组，支持逐台勾选、搜索、排除。门禁类（如“开一下 26 楼大门”）生成待人工确认的开门草案。全程不下发控制。

**Blocked by:** [01: Java 业务定义与通用 Node 执行引擎](01-java-business-generic-engine.md)

**Status:** ready-for-agent

## 说明书章节

第 1 章 1.1（公司助手权限范围与缺区域分类时需追问定位）；第 2 章 2.1（公司检索示例）、2.3（照明与门禁、混合范围与保留区域）、2.4（批量预览、台数、分组、勾选/搜索/排除与确认）；第 5 章 5.1（设备清单七类与位置分组）。逐条案例见 [验收矩阵](../acceptance.md)，完整规则见 [规格](../spec.md)。

## 本票必须自包含的规则

- 目录只来自当前授权范围；不得使用客户端或模型提供的设备权限，不得混入其他用户或其他来源的设备。
- 七类目录必须按同一授权口径可检索；分页、去重、物理绑定与目录完整性保持 Runtime 既有语义；上游失败时返回明确业务错误，不返回空成功或假目录。
- 目标描述有歧义或在多台设备间不唯一时必须追问或列候选，不自行猜测；位置是公司范围的必要消歧条件。
- 范围减法在服务端完成：先展开匹配集合，再扣除明确保留/排除项，再计算已符合目标无需操作的设备；模型不得自行拼装最终设备 ID 列表。
- 确认单必须显示拟执行、排除、无需操作三类台数，三者与实际清单一致；按楼层/位置分组；逐台勾选、搜索、排除生效。
- 同时包含照明与空调时，两类设备都在同一份草案中各自呈现目标状态，不因类型混合而丢弃一类。
- 门禁草案必须列出设备清单并在“执行操作”前停止；未确认不产生任何开门指令。
- 公司总览/设备目录展示的类别与对话检索使用同一授权事实，不出现目录有而对话无、或对话越权的分裂。
- 本票不执行真实控制、不创建任务、不发送通知。

## 验收条件

- [ ] 真实公司账号在微信开发者工具中检索七类设备，前端显示的真实数量与授权目录一致；抽检每类设备名称/位置/状态来自真实上游。
- [ ] 输入说明书 2.1 的公司检索示例（如“26 楼运营办公区的灯现在什么状态”），前端列出真实候选并读取状态；无该目录时如实说明，不伪造。
- [ ] 输入“关闭 26 楼各办公区的照明和空调，保留过道区域照明”，确认单同时包含照明与空调，过道照明不出现在拟执行集合；台数三分类自洽，按位置分组正确。
- [ ] 逐台勾选、搜索、排除在前端生效；排除后拟执行台数同步减少，服务端下发集合与界面一致。
- [ ] 输入“开一下 26 楼大门”，生成列明设备的门禁确认单，未确认前无任何开门请求；确认入口存在但本票验收不点击执行。
- [ ] 越权/跨来源设备不进入候选或草案；构造缺失设备或越权引用时返回明确错误而非空成功。
- [ ] 全程无生产控制、无任务、无通知；证据包含截图、脱敏诊断、账号、来源、区域、构建 ID。
