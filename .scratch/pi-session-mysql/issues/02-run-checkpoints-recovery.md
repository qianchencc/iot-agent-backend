## Acceptance criteria

- [ ] 运行在调用工具前取得 Java 权威写入资格；旧实例的追加、工具回调及终结均被拒绝，不仅在整轮结束做 CAS。
- [ ] 完整消息和工具意图/结果形成持久检查点，不能只在整轮结束保存，也不逐 token 开数据库事务；事务不跨模型或上游调用长时间持有。
- [ ] 相同提交标识/相同内容返回同一提交；相同标识不同内容冲突；提交成功但响应丢失能查询并确认，不盲目重跑模型或业务工具。
- [ ] 在工具意图后、工具结果后和终态前分别中断真实隔离进程：已提交记录保留、未知副作用不自动重发，未来上下文的工具调用与结果仍合法配对。
- [ ] 公开成功终态只能在相应上下文与轮次终态持久化确认后出现；故障界面可解释，不泄露 SQLite/内部 scope/路径等实现细节。
- [ ] 模型、MySQL、Redis 或私有网络失败均不会通过清空历史或自动创建空会话掩盖；Redis 失效不能丢失已提交会话。
- [x] 真实开发者工具完成中断/替换后的业务追问；U07/U08及F15分别保留故障、恢复结果，未执行生产控制或创建生产任务。

### 长会话压缩发现的真实业务缺口

U17暴露128k模型收到约165k历史，输出预算被挤压为128 token且无公开正文。原生Pi压缩恢复了回答，但U19仍丢失先前报告身份、合计及证据限制，保持失败，不因压缩单测通过而验收。

原生SDK每条工具结果仅序列化前2000字符，实际报告身份与证据限制出现在更后。Java已从绑定会话事件解析报告身份并校验tenant/owner/source/conversation，重投影不可变历史事实；不赋予当前设备权限。Node仅接收Java通用压缩说明并使用原生压缩。U23、F11/F15/F18已补报告数值、限制及引用追问截图；原失败仍保留。
