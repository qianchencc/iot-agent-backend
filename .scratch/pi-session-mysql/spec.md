# Pi Session 统一 MySQL 持久化

Status: ready-for-agent
Execution: not-started
Date: 2026-11-02

## Problem Statement

客户已有 MySQL 并由 Java 团队维护，但新后端的 Pi Session 仍在 Node 本地 SQLite 中。一次真实小程序对话已出现 writer lease was lost：答案可见却不能可靠保存上下文。当前存在两套持久化运维、Node 本地卷依赖和不一致的恢复路径。旧运行实例并未因本规格发布而修复。

## Solution

Java 统一管理业务事实和 Pi Session 的持久化权威；两者逻辑分开、同由 MySQL 承载。Node 使用固定版本 Pi 的原生会话接口，经受控私有协议访问 Java 会话模块，保留模型循环和上下文处理，不直接访问数据库。用户继续使用原小程序入口，已有历史可继续对话；Node 更换后从已提交状态恢复，无须清空历史或恢复本地 SQLite 文件。

## User Stories

1. 作为客户 Java 维护者，我希望会话持久化与业务库由 Java 管理，以免跨语言维护两套数据库。
2. 作为运维人员，我希望 Node 不依赖本地持久卷，以便替换实例而不丢历史。
3. 作为用户，我希望旧会话迁移后能继续追问，以便不重新说明设备和业务上下文。
4. 作为用户，我希望 Office 与 Company 历史隔离，以免引用其他来源设备或事实。
5. 作为不同租户或账号，我希望无法猜测会话标识读取、写入或删除他人上下文。
6. 作为用户，我希望重启后保留工具调用及其真实结果，以便提案不因重试重复生成。
7. 作为用户，我希望会话保存失败时明确知道本轮未可靠完成，而不是只看到成功答案。
8. 作为用户，我希望断线重连不重复出现已经提交的消息和草案卡片。
9. 作为用户，我希望过期草案仍需重新核验，不因恢复历史自动下发。
10. 作为用户，我希望任务确认单能恢复，但不会因恢复会话自动创建任务。
11. 作为维护者，我希望压缩摘要、分支、工具配对和操作日志不在迁移时损坏。
12. 作为维护者，我希望并发和过期实例的写入被明确拒绝，而不是覆盖较新状态。
13. 作为运维人员，我希望能验证 MySQL 备份的实际恢复结果，而不是保留不可用备份按钮。
14. 作为维护者，我希望升级 Pi 时能运行官方存储一致性测试发现语义变化。
15. 作为客户，我希望业务工具、指引和权限的迭代仍只改 Java，不因本次迁移转回 Node。
16. 作为验收人员，我希望看到重启、导入和追问后的真实小程序业务结果及截图，而不是 HTTP 成功或测试数量。

## Implementation Decisions

- 固定 Pi 0.84.4；实现其公开 SessionRepo / SessionStorage。Entry、LaneRecord、共享 sequence、parent 链、lane、标签、名称、用量、fork、日志查询、开放操作与不可变读取遵循上游，不只实现当前 appendMessage 调用。
- 主要验证 seam 是 Node 的 Pi 会话仓储入口，测试必须穿过实际私有协议与 Java/MySQL。Java 会话模块隐藏表结构、事务、标识分配及写入约束；不暴露任意 SQL 或可执行代码。
- Java 从已核验的租户、主体、source、conversation/run 绑定派生访问范围。Node 不得靠传入任意 sessionScope、owner 或 tenant 获得权限。管理操作使用独立授权。
- Pi 的 opaque-string 标识不强制 UUID，不大小写合并、不静默截断；持久化按上游支持的字符与 JSON 语义保真。Pi 表与现有业务 task/事件表分开，避免同名冲突。
- Node 仅持有活动 run 的暂态内存；重开必须读取权威已提交状态，不能复用已经失去所有权的会话对象。
- 运行入场在工具调用前获得服务端会话写入资格；后续写入、工具回调和终结校验 run 所有权/代次。仅用末尾 CAS 不能防止两个模型轮次提前重复执行工具。
- MySQL 使用短事务提供原子追加、有序读取及幂等提交。同一提交标识和相同内容重试返回原结果；同标识不同内容、旧版本或过期所有者必须拒绝。HTTP 响应丢失先查询提交状态，不盲目重跑模型或工具。
- 在用户输入、完整模型消息、工具意图/结果等可恢复检查点提交，不逐 token 持久化、不仅在整轮结束保存。工具进入执行前留下稳定调用标识和意图，返回前保存可核对结果；未确认副作用不自动重发，不承诺外部系统 exactly-once。
- 公开成功终态必须晚于对应上下文及终态事实持久化确认。流式文字可先显示，但保存失败时该轮为未完成/失败，诊断不泄露内部路径、会话标识或凭据。
- 中断运行默认结束为可解释的中断状态，不自动重放业务工具；已有工具结果按稳定标识恢复，未确认结果按未知处理。新一轮恢复的上下文必须保持工具调用与结果配对，不伪造成功结果。
- Redis 可失效而不丢 Pi Session。协调状态不能取代 MySQL 中权威写入版本及提交事实。
- 迁移仅针对新 Java 后端 sidecar 的已有 SQLite 会话，不迁移或修改可靠原 Runtime 的生产数据。先一致性备份，再停写导入；现有业务事实不复制、不重建、不重复执行。
- 从 Java 事实校验旧会话的归属，不根据孤立 scope 字符串猜测租户。不确定映射进入只读隔离清单；任何仍在使用的会话未能校验映射均阻止切换。只读源及备份完整保留。
- 正式切换使用单一 MySQL 权威，无双写、自动 SQLite 回退或长期兼容别名。迁移工具可单独读取旧 SQLite，但不成为运行中 Node 的依赖或公开功能。
- SQLite 专用的管理备份、恢复、磁盘容量和 writer-lease 手工恢复入口随调用方一并切除。Java 管理面显示真实 MySQL 会话状态；数据库备份恢复交给受控运维流程，不提供任意路径或 SQL 执行入口。
- 全部源码在现有业务 worktree 的集成分支推进；迁移完成前不把中间源码部署为用户可测试版本。隔离构建完成后一次切换，原缓存工作区、原开发者工具窗口和生产 Runtime 不动。
- 本次 Node 存储适配属于通用引擎升级，需要新的源码/构建基线；旧的 Node 字节不变证据只证明旧版本，不能挪作新版本证明。业务定义仍留 Java。

## Testing Decisions

- 运行该固定版本未修改的 createSessionBackendConformance，覆盖真正的 Node→Java→MySQL，而非只跑 mock、内存实现或 Java 仓储测试。版本不支持的语义必须显式报告，不能删减用例换绿。
- 既有模式包括独立 Node 进程契约、Java 身份和事件重放契约、独立 MySQL/Redis 夹具；沿用其隔离和真实错误语义。新增测试只锁定消费者可见行为，不测试源码、转发或措辞。
- 注入应答丢失、旧 writer、并发、进程退出及 Redis 中断，验证已提交事实、顺序和不重放；测试不访问生产写接口。
- 旧库导入比较所有会话的规范记录、标识/序号/parent、分支、统计及 Pi 构造出的模型上下文；只比总数不足以通过。
- 独立开发者工具执行迁移后旧会话继续追问、节点替换、Office/Company 隔离、草案/任务提案和真实报告引用；截图是业务验收证据。既有业务缺陷不得算作迁移通过，也不得用伪造内容绕过。
- 详细操作与完成判据见同目录 acceptance.md。全程不下发生产控制、不创建生产任务、不发送生产通知。
- 所有实现完成后仅做一次最终 Standards/Spec 审查，不启动子代理，不做中途反复审查。

## Out of Scope

- 重写 Pi、升级 Pi Durable 1.x、引入 PostgreSQL/Kafka，或修改原 Runtime。
- 把 MySQL 作为新的物联业务查询工具；本规格只涉及会话持久化。
- 开发新的业务功能、重新设计缓存平台，或把既有业务恢复票据直接标完成。
- 自动续跑未确认的业务副作用、生产执行演示，以及对所有149条说明书案例重新加硬门禁。

## Further Notes

本规格为规划交付，不是实现/业务验收结论。客户目标和方向已明确；私有协议的具体字段、表结构及索引由01沿上游契约落定，不能先造一层万能数据服务。旧 ADR 的 SQLite 选择由 ADR0005 的目标方向取代，运行实例在06完成前仍不算迁移成功。社区证据见业务恢复目录的 research-pi-mysql-session.md；新的状态必须与原业务恢复状态分别维护。
