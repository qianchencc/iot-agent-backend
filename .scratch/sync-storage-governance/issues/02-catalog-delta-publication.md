# 02: 完整展示目录差量发布，避免无变化整表重建

**What to build:** 用户仍读取最新完整设备目录；同一份完整目录重复同步不删除重插全部正文，真实新增、改名、位置变化和移除准确发布。

**Blocked by:** None (can start immediately).
**Status:** completed
**Execution:** 已实现、定向回归及隔离真实MySQL验证；2026-11-12已进入固定Java3381。真实微信页面未复验。

## 前因后果

完整设备目录服务设备展示及安全台账当前设备资料，按网关实例／租户共享；它不是某个用户的操作授权。后台先取得完整列表，再在事务中发布，使读取不会见到半批目录，这个可靠性设计应保留。

当前每次成功发布都删除该目录全部行，再插入完整新列表，即使名称、位置和成员完全相同。自然观察窗口中，完整展示目录的行事件约0.135MiB；该数据只是一个窗口，不是全天占比或本票节省承诺。

## 目前问题

相同内容反复重建造成SQL、索引及行写入成本；关闭binlog后这些成本仍然存在。优化应针对重复正文，而不是取消完整采集、失败保护或同步成功记录。

## 改进目标与实施范围

1. 在既有完整列表校验、目录进度锁和发布事务内按稳定来源设备ID及类型比较新旧内容。
2. 新成员插入，名称／位置等实际内容变化时更新，完整新列表确实移除的成员删除；完全相同的正文不改。完整成功空列表仍能正确清空目录。
3. 保留成功时间、下次同步、失败状态、旧尝试不能覆盖新尝试等进度语义；失败或不完整结果不能被当作空列表。
4. 读取继续返回同批正文与元数据；共享展示目录不扩大用户控制、能耗、安全或视频权限。当前设备资料改变不得重写原告警名称／时间。
5. 复用现有目录实现、事务和入口，不新增缓存、通用差量框架或数据库表。修改只覆盖完整展示目录；用户授权目录归03。

## 非目标

不减少采集频率、不做上游增量协议改造，不重新设计用户授权；不改任务、控制和台账事件语义；不为观察效果触发客户上游请求。

## 验收标准

- [x] 相同完整目录重复发布，正文行无插入／删除／内容更新，成功进度仍正常推进。
- [x] 单设备改名／改位置只改变目标正文；新增、移除、相同ID不同类型、真实空列表均正确。
- [x] 不完整列表、来源失败和事务故障保持上一完整结果及正确失败状态，不刷新假成功。
- [x] 慢旧批次不能覆盖较新批次；保留同一进度行锁下的读取／发布及权限核验。
- [x] 公司目录与安全台账当前资料通过原公开读取入口正确呈现；原事件内容、个人授权及控制绑定不变。
- [x] 合成来源回归及隔离真实MySQL验证通过，不用净行数或affected-row单独证明。
- [x] 既定后台采集节奏保持，普通读取来源调用增量为0；模块说明和执行证据已更新。

## 最终预期效果

前端仍看到同样完整、及时的目录；后台不再为相同目录重建所有正文。收益主要是持续写入与索引维护成本下降，不承诺数据库现有文件缩小或固定下降百分比。
