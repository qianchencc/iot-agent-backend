# 01: 关闭无实际用途的binlog并回收现存日志空间

**What to build:** 本项目没有实际日志消费者的MySQL实例不再生成binlog；已有无用途日志正规清理，任务等本地记录和正常事务不变，交付真实释放空间与配置生效证据。

**Blocked by:** None (can start immediately).
**Status:** completed
**Execution:** 2026-11-11已在原容器生效；未重建容器、未更换数据挂载或凭据。

## 前因后果

用户最初发现工作目录约5GB。清理旧产物后约1.80GB，进一步发现独立业务MySQL卷不在工作目录内，约20.80GB中有19.37GB累计binlog。日志记录修改过程，不等于19GB独立业务数据。

用户随后明确：本系统主要保存少量任务等本地记录，以及方便前端读取的可重建上游副本；不应为副本设计时间点恢复、备份链和复杂迁移。旧方案将副本视为不可丢失资产的方向已撤回。

## 目前问题及证据边界

- 当时业务实例启用ROW/FULL binlog、30天自动过期；不是完全没有清理。
- 当时无已登记或在线复制连接，不据此宣称所有潜在离线消费者已经排除。实施前核对实际部署和真实依赖，不构造假想需求。
- 本地3307实例与业务3338实例分属不同存储位置；业务容器历史启动来源与当前仓库配置可能不同，不能直接套Compose文件重建导致挂载、端口或凭据改变。
- 上述体积为2026-11-11快照，不是执行当天大小。当前运行、目录清理与独立业务卷必须分别核实。

## 改进目标与实施范围

1. 识别实际服务本项目的实例、schema、数据挂载和部署配置；只核实真实复制／订阅依赖。存在真实依赖时明确该实例阻塞原因，不停消费者、不以假想恢复需求阻塞其他可处理实例。
2. 在无实际依赖的实例上配置禁用binlog，保证后续正常启动仍禁用；不能只改一个会话。持久配置与实际部署一致，沿原生启动方式，不新增启动器。
3. 使用对应MySQL版本支持的管理操作处理已有日志及索引；如需启动参数变更或重建容器，保留原数据挂载、配置、凭据和端口，按受控窗口执行。不得启动空库替代旧库或重启不属于本工作区的实例。
4. 正规清理确认无用途的日志副本；不再把19GB原日志复制或归档到另一处冒充空间回收。此前工作目录内的旧binlog归档单独列明保留／清理结果，不混入业务卷收益。
5. 保留正常事务、redo／undo及既有提交持久性；任务、计划、会话、配置、报告等本地记录不清空。启动或重启前检查在途业务，避免打断已确认操作；不触发设备动作或客户上游诊断请求。
6. 核对持久化配置已生效及实际磁盘变化，更新运行说明和执行证据。正常应用后台同步不因本票降低频率或缩减范围。

## 非目标

不建立恢复点目标、全库恢复链或额外备份项目；不关闭MySQL内部崩溃恢复，不直接删除数据库内部文件或数据卷；不删任务或历史事实；不修复／清空缺表空间的旧预览库；不等待代码优化票完成。

### 2026-11-11实际执行

- 操作范围：本项目local MySQL `dc7a7f4e0e0a`（3307，`var/docker/mysql`绑定目录）及business MySQL `5846c6eae356`（3338，原命名卷`iot-agent-business-preview_business-mysql`）。Redis、其他工作区及缺表空间的旧预览库未改。
- 前置检查：两实例`SHOW REPLICAS`、复制连接状态及Binlog Dump连接均为空；实际配置无日志订阅者。运行中的Pi writer为0，任务阶段无RUNNING／EXECUTING／DISPATCHING。
- 生效方式：原容器增加`/etc/mysql/conf.d/99-iot-no-binlog.cnf`，内容为`[mysqld]`下`skip-log-bin`，通过`mysqld --validate-config`；仓内两份Compose同时设置`command: ["mysqld", "--skip-log-bin"]`，两份`config --quiet`通过。未用当前Compose重建历史容器，避免其挂载／秘密注入方式差异。
- 正规回收：开启状态下先`FLUSH BINARY LOGS`，再`PURGE BINARY LOGS TO`刚生成的活动文件，随后逐个干净重启原容器。重启后两实例`@@log_bin=0`、`@@sync_binlog=1`、`@@innodb_flush_log_at_trx_commit=1`。自然同步恢复后仅各留181字节末尾日志，没有把旧日志搬到新归档。
- 业务卷：操作前20,613,804KiB，操作后1,397,964KiB；释放19,215,840KiB，约19.68GB。当前约1.43GB，而非旧快照的20.80GB。
- local数据目录：401,912KiB，未清业务数据；此前单独留下的旧binlog归档`var/mysql-binlog-archive-20261111.tar.gz`已删除，另释放415,225,967字节。工作目录本轮测得1,346,780KiB（约1.38GB，含构建产物）；不把工作目录和外部业务卷相加冒称“纯仓库”。
- 前后数量相同：任务28、阶段38、计划10、提案82、通知17、报告14、Pi文档195、会话83。未向客户上游发诊断请求、未造任务或控制。
- 结论：主要容量问题已处理；剩余空间为正常事实／索引／数据库内部文件及开发产物。宿主机Docker虚拟磁盘是否即时收缩未作承诺；不为这一步额外重启Docker或其他服务。
