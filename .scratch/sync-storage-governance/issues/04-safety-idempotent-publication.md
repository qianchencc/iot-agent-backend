# 04: 安全事件同值不重写，保留完整采集与修订语义

**What to build:** 安全台账重复同步相同事件时不重写正式正文，真实修订及时更新；事件原名／时间、当前设备资料、分页与授权行为保持，失败仍保留上一完整结果。

**Blocked by:** None (can start immediately).
**Status:** completed
**Execution:** 已实现、回归及隔离真实MySQL写入／并发验证；2026-11-12已部署固定Java3381。真实微信台账页未复验。

## 前因后果

安全台账由后台采集，前端和Agent从本地读取。原事件名称、身份、发生时间及alarm/report与当前设备名称／位置分离，不能为了展示资料刷新而改写历史事件。

当前三类台账分别领取尝试、完整暂存并事务发布。同一类当前／全量使用既有尝试保护；成功、覆盖和发布版本另存进度。正式事件发布却对同键无条件更新原名、alarm、report、同步及更新时间，完全相同的事件也重复落库。

## 目前问题及为什么适合局部改进

自然窗口中安全暂存和正式事件的行事件分别约0.113／0.100MiB。这里不是主要19GB日志的全部来源，也不承诺固定收益；但已有独立尝试保护和成功进度，适合在不新增结构的前提下减少正式正文重复更新。

这与电表／环境逐样本时间同时承担迟到保护的路径不同，不推广成统一“值没变全部跳过”的框架。

## 改进目标与实施范围

1. 保留完整分页暂存、每类领取和原发布事务；仅插入新事件或更新真实变化的原事件名称、alarm、report等既有正文／质量字段，采用NULL安全且符合原类型的比较。
2. 完全相同事件正文不重写，已有行创建时间保持；该类同步成功、覆盖及发布版本照常推进，对外新鲜度仍反映实际成功采集。
3. 明确事件行同步／更新时间与进度成功时间的含义，核对其消费者；不为了保留多余行更新时间重写正文，也不把事件发生时间改成同步时间。
4. 仍按原事件身份去重，同一类当前与全量保持现有尝试保护，三类分别提交；不用新增日志表或发布水位替代已有机制。
5. 原事件与当前目录资料分离，告警监控候选和回放窗口仍按原线索、原事件时间及独立视频授权计算；report不解释为已恢复／处置。
6. 用户安全授权、类别与物理授权集合共享限制保持；全量缺行不直接删除历史事件，失败不推进成功覆盖。

## 非目标

不优化电表或环境的逐记录时间保护，不删除暂存、不缩采集范围，不改告警业务含义或补造摄像头历史关系；不新增通用幂等框架、事件审计体系或灾备机制。

## 验收标准

- [x] 完全相同事件重复同步，正式正文无新增／更新／删除，成功进度正常推进；暂存操作单列。
- [x] 新事件／真实原名、alarm、report修订保持原身份语义；大小写名称及NULL标志双向变化通过。
- [x] 后页失败及事务故障保留旧正文和原成功状态，不泄漏半批。
- [x] 真实MySQL验证旧当前尝试迟到不能覆盖更新全量、换证中的旧凭据不能发布；既有撤权回归保持。
- [x] 台账公开列表／详情／分页、原事件与当前资料、告警候选及显式选择后的回放准备回归通过；未取真实流或执行控制。
- [x] 共享事实仍受本人授权、租户／来源及相同物理集合约束；完整授权移除不物理删除旧事件。
- [x] 合成来源及隔离真实MySQL证明正文行操作下降，不以H2、总行数或affected-row单独证明。
- [x] 普通读取来源调用增量为0；时间字段语义、模块说明及证据已更新。

## 最终预期效果

用户仍看到完整、及时且含义正确的台账，真正修订正常生效；相同历史事件不再仅为刷新同步时间而重复改写正文。仍保留必要暂存和进度，收益是局部数据库写入减少，不承诺零写或表文件缩小。
