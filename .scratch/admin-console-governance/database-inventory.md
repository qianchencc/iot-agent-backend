The categories overlap: the three task tables are included in the 24 SQL-resource definitions. No production Node-side `CREATE TABLE` was found in the investigated sidecar; Node uses Java’s private session API.
- MySQL storage is **disabled by packaged default**. Schema and JDBC writers are conditional on `agent.storage.mysql.enabled=true`; a table definition or local row count does not prove that a writer is active in a particular deployment. `src/main/resources/application.yml:23-27`, `src/main/java/ltd/qianc/iotagent/storage/internal/StorageConfiguration.java:37-56`.
- Parent-provided local, read-only evidence records 27 tables in `iot_agent_business` and 25 in `iot_agent_mysql_final`; the latter lacks the two read-snapshot tables. It is a local snapshot, not production or business acceptance: `.scratch/admin-console-governance/evidence/local-mysql-metadata.json:1-6,3810-4079`.
- The existing admin API exposes configuration revisions and Pi journal **health**, not a user-centric browser for the business tables. A user-first design must join ownership across columns, JSON, conversations, tasks and Pi scopes; `owner_key` is a hash, not a displayable user identity.
- `audit_events` is **not a complete, immutable platform audit trail**: the located producer is action-draft-specific and optional, and duplicate event IDs overwrite payload/type. Configuration changes have a separate revision history with actor `"operator"`.
- Pi headers, entries and operation records are **not separate relational tables**: Pi’s native JSONL codec stores them in virtual files whose serialized content is split into `pi_session_chunks`. Neither Pi journals nor ordinary business JSON are application-encrypted by these stores.
- A consequential report linkage drift exists: the checkpoint bridge writes `origin.taskId`, while task report retry/projection lookup searches root `$.taskId`. Do not claim all task reports are discoverable from that lookup.

## Architecture and ownership

**Bootstrap.** The shared initializer runs `agent-facts.sql`, `admin-configuration.sql`, `agent-allowlist.sql` and `read-snapshot-barrier.sql`; the candidate initializer separately runs its resource, and `TaskSchemaInitializer` applies task additions and creates task tables rather than running the non-idempotent `ALTER` resource directly. Pi creates its four tables in its service constructor. `CREATE IF NOT EXISTS` does not itself migrate all possible historical column/index drift. Sources: `StorageSchemaInitializer.java:17-26`; `IotAdapterConfiguration.java:22-34`; `DeviceCandidateSchemaInitializer.java:17-20`; `TaskSchemaInitializer.java:26-46`; `JdbcPiSessionService.java:35-64`.

**Owner identity.** For verified users, `PrincipalInfo.ownerKey()` hashes tenant, identity realm and principal ID; the fixture fallback hashes tenant plus authorization. The database commonly stores this hash, not the underlying principal ID or a user display name. Cross-source attribution must retain `source` (`office` and `company`) rather than treating owner hash as a complete user profile. `src/main/java/ltd/qianc/iotagent/auth/PrincipalInfo.java:16-31`.

**Inventory conventions below.**

- **P** = primary key; **U** = unique key. Unless stated otherwise, baseline tables use auto-increment `id` as P.
- **B/F** = exact parent-observed local row counts in business/final schemas respectively; `—` = table absent. Counts are not evidence of current production writers or successful flows.
- “Current admin” means the existing `/api/admin` controller, not ordinary owner-scoped application endpoints. Except configuration revision views/history and aggregate Pi health, no table-specific admin data endpoint was located. Any per-user/table inspection mentioned below is **proposed**, not implemented.
- “No application encryption established” means the inspected JDBC adapter serializes/stores the value without application-level encryption; it does not establish MySQL/disk/backup encryption settings.
