# 51: 历史能耗滚动须复用已取得的日期数据

**What to build:** 用户在能耗统计中快速回看较早日期时，后端复用已取得的重叠历史，前端优先取得当前查看日期；不因窗口结束日变化便重复准备大段历史，不让当前日期一直排在已离开的窗口后。保留电表明细、完整采样及比较口径。

**Blocked by:** None (can start immediately)
**Status:** ready-for-human

用户已授权完成本票。实施复用日期历史与当前目标优先，不改外部查询契约；47–50号票的非阻塞读取与统计完整性继续作为基线。公共回归沿用能耗组合器接口、前端历史补块模块，以及真实HTTP/微信页面，不测试private实现。

## 已核实的读取链路

- 前端首块只取30天，180天条带包含未取得数据的占位。历史补块一次90天，结束日由当前缺口决定，并非统一固定日期块。
- needRange将补块加入FIFO队列，pump逐个await完成；可见范围变化和选日不会把当前目标提到队首。快速拖动的额外UI排队影响由此可推断，本轮未量化其实际毫秒数。
- 前端历史日请求使用默认60秒复用、5分钟占位的查询级内存快照；重新打开会清理面板合并的数据并从首块重建，不能把一次面板内已合并历史当成长期复用。
- 后端ReadSnapshots按身份、来源、operation及完整query缓存整份响应；days/end改变即不同键。明确结束于过去的查询确实使用上海下一日刷新策略，已有结果保留给前台，故障时不因到期强迫前台等待。
- COMPANY_ENERGY_DAILY缓存未命中时重新进入能耗组合器，建立授权电表范围，并从统一计量流第0页开始扫描至所需起点。该内部rawHistory读取直接走网关，没有复用另一查询已扫描的历史基础数据；日期越早，需越过的近期记录越多。

## 对原策略的判断

“历史深夜更新、当前约一分钟更新、前端只问backend”的责任划分继续有效。缺口不在增加另一种TTL，而在缓存内容与业务访问方式不匹配：整份查询快照不等于可重用的日期历史，180天可滚动占位也不等于180天已经备齐。后台异步只解决HTTP不被同步拖住，没有消除首次数据等待或重复历史扫描。

## 实施方向

1. 在能耗模块内部按固定日期块复用已取得的计量历史及必要日统计；窗口查询在已持有内容上组合，后台只补缺块。日期块不是上游页号：新增记录会使页号漂移。保留日期边界采样、计量日边界和缺失/截断标记，不能把累计读数简单相减或用日合计替代所有比较口径。
2. 继续沿用历史日更新、当天约一分钟更新；常用可浏览范围由后台逐步补齐。更早且从未取得的数据允许明确准备，不承诺无限历史首次瞬时可用；不新建全量预热/复杂缓存平台。
3. 前端补块使用稳定日期划分、合并重复需求，优先当前选中/可见窗口，移除尚未开始且已无查看需求的排队任务；已完成数据保留，不增加无限并发。
4. 先用相邻窗口重复读取和快速跨窗浏览证明复用，再检查功能与边界；不得以扩大线程数、延长等待或缩小窗口作为修复。
