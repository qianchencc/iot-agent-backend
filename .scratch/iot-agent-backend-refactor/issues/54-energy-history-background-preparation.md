# 54: 翻阅历史前由后端准备近期及去年同期能耗

**What to build:** 用户进入能耗业务后，由backend在后台逐步备齐最近24个完整自然月的历史结果及基础月块，覆盖默认180天和去年同期；用户之后直接翻到未在页面打开过的月份，不再首次才触发整月采样扫描。前端继续只读backend，不等待后台全程完成、不加长轮询、不减少电表或统计能力。

**Blocked by:** 51（后端历史月块、普通读与后台更新分离已具备；可立即开始）
**Status:** ready-for-human

- [x] 首次普通读取只返回当前已有结果；历史准备由既有有界执行器异步执行，不能阻塞HTTP或占满前台所需工作线程。
- [x] 同一身份/来源的重复访问仅登记一个后台准备工作；沿用历史深夜更新和当前约60秒的固定模板，不新增缓存平台或前端上游认知。
- [x] 准备最近24个完整月的自然月请求和基础数据；超出该范围仍可查询，但首次允许明确准备，不宣称无限历史瞬时可用。
- [x] 准备完成后禁止上游读取，直接请求此前未访问的历史月份，仍返回完整日值和逐表明细；失败不能缓存为零值或伪完整，身份隔离不变。
- [x] 当前开发者工具同一账号触发后台准备后，用未打开过的历史月份验证数据可读耗时、43表数值及正常恢复；真实页面浏览由用户验收。

## 现状与决策

51已消除错误空月、重复窗口全量扫描及已有块等待当前月更新，但未实现原Runtime的历史提前准备。实测首次历史窗口仍需16.8秒，不能用已命中的约0.5秒证明翻阅体验已解决。

采用一个业务级后台准备工作，复用现有ReadSnapshots、月份组合器及身份边界；先准备近月再向较早月份推进。通过相同自然月查询键保存日统计结果，同时填充51的可复用月块。背景失败保留失败状态并沿用既有重试，不影响已经可读的数据；不新建队列、线程池或持久数据库。

## 用户验收结论

用户在当前开发者工具实际翻阅较早能耗日期后反馈“基本没什么问题”。此前“未计算”问题已消失，较早日期加载慢的问题在后台准备设计落地后未再报告为阻塞。此结论是页面业务验收证据；后端回归和HTTP验证仅作为实现证据，不替代用户验收。

## 核心设计记录

- **前端只读backend现有结果。** 前端不识别上游、不等待上游同步；首屏登记后台准备后立即显示backend当前已有状态。
- **历史按自然月准备，按自然月复用。** 后端以同身份、来源和准备区间去重后台工作，近月向前准备24个完整月；普通查询复用月块和日统计，不把一次查询结果当作历史基础事实。
- **刷新与准备分离。** 当前数据按约60秒模板更新，完整历史按上海深夜模板更新；历史准备只负责首次补齐，不能变成每次翻页的同步门槛。
- **完整性优先。** 上游分页异常、截断、权限失败不得缓存为零值或“无数据”；已有完整结果在后台刷新失败时继续可读，并保留失败状态。
- **范围与身份隔离。** 月块和日统计按租户、凭据代次、来源及授权电表集合隔离；前端看不到上游，也不能声明未同步的撤权已经发生。
- **范围边界。** 最近24个完整月覆盖默认180天和去年同期；超出范围仍支持查询，但首次准备时间不承诺瞬时完成。
