# 40: 物联 Agent 业务性能 SLA 与缓存地图校正

**Type:** grilling
**Status:** open
**Blocked by:** 33, 34, 36, 39

## Question

以业务体验而不是后端实现作为约束，冻结以下目标：

1. 用户打开物联 Agent 页面到首屏所需数据可用不超过 3 秒；
2. 后续主要子页面/业务入口通常不超过 1 秒等待；
3. Agent 各类设备查询工具执行不超过 1 秒；
4. 用户手动刷新到完成不超过 2 秒。

需要把 SLA 分解为：frontend 快照命中时间、backend 最新快照命中时间、backend→upstream 刷新时间、低频查询冷启动、Agent tool bridge/模型等待是否计入；并决定哪些数据必须预热/定时刷新/建立本地索引，哪些业务不能在交互路径上等待上游全量读取。

## 业务约束对地图的直接修正

- 3 秒首屏意味着首页展示数据不能依赖打开页面后串行全量上游读取；backend 必须有可读的最新快照，frontend 先落位并并行对齐。
- 1 秒子页面意味着常规路径应命中 frontend 或 backend 快照/索引；不能把低频请求触发上游作为普通交互默认路径。
- 1 秒设备查询工具意味着候选/状态查询需要使用 backend 预热快照或本地可检索索引；不得在 Agent 工具循环内临时拉取多套目录后再返回。
- 2 秒手动刷新意味着 frontend force 只能重新取 backend 最新结果；若要求同时强制 upstream refresh，必须证明上游读取也能稳定落在该预算内，否则应采用 backend 后台更新 + 前端完成状态表达。

## 需要形成的验收证据

- 冷启动首屏：无 frontend 快照、backend 已有/没有最新快照的分支耗时；
- 热打开：frontend 命中耗时；
- 子页面：backend 命中耗时；
- 手动刷新：前端绕过快照后 backend 响应耗时；
- 设备候选/状态工具：工具 bridge 本身耗时，不把模型生成时间混入，除非业务另行确认；
- 上游慢、部分失败、backend 后台刷新未完成时的用户可见结果。
