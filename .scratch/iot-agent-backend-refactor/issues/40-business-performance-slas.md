# 40: 物联 Agent 业务性能目标与缓存地图校正

**Type:** grilling
**Status:** resolved
**Blocked by:** 33, 34, 36, 39

## Question

以业务体验而不是后端实现作为约束，形成以下**目标值与检查基线**，不是为所有场景建立严格、复杂的策略：

1. 用户打开物联 Agent 页面，首屏可见数据尽量在 3 秒内出现；
2. 后续主要子页面/业务入口通常尽量接近 1 秒；
3. Agent 设备查询工具执行尽量接近 1 秒；
4. 用户手动刷新尽量在 2 秒内完成。

时间目标用于发现明显的业务等待和后端逻辑问题；达不到时先定位慢在哪里，再做必要的局部矫正，不为追求数字引入过度预热、复杂分层或特殊缓存策略。

## 业务约束对地图的直接修正

- 首屏目标要求首页展示数据不要默认串行等待上游全量读取；优先利用现有 frontend/backend 快照和并行读取，必要时再补充简单的 backend 准备。
- 子页面目标要求正常路径尽量命中已有快照或轻量读取；不要求所有业务都提前建立复杂索引。
- 设备查询工具目标用于发现明显的目录重复读取、串行上游调用和无谓工具循环；先做必要的 backend 逻辑矫正，不预设复杂缓存体系。
- 手动刷新目标表示 frontend force 后应尽快拿到 backend 当前结果；不把它升级成强制 upstream refresh。
- 所有时间目标都允许受上游、网络和数据规模影响；验收重点是用户体验是否顺畅、是否存在可避免的等待。

## 需要形成的验收证据

- 冷启动首屏：无 frontend 快照、backend 已有/没有最新快照的分支耗时；
- 热打开：frontend 命中耗时；
- 子页面：backend 命中耗时；
- 手动刷新：前端绕过快照后 backend 响应耗时；
- 设备候选/状态工具：工具 bridge 本身耗时，不把模型生成时间混入，除非业务另行确认；
- 上游慢、部分失败、backend 后台刷新未完成时的用户可见结果。

## Answer

- 首屏目标按“首屏可见数据”检查，不要求隐藏/详情模块同时完成。
- 设备查询工具目标只观察 Tool Bridge/Java 业务执行耗时，不计模型推理、网络传输和整轮 Agent 文案生成。
- 子页面和手动刷新目标用于检查明显等待，不作为所有场景的严格硬门槛。
- 这组目标优先于后端实现结构，但不要求为每个目标设计复杂策略；先按现有 frontend/backend 缓存和简单并行/复用逻辑解决可见问题，再对确有瓶颈的能力做局部优化。
