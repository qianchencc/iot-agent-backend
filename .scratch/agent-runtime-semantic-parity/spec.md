# Java 业务定义与 Runtime 行为语义对齐

Status: ready-for-agent
Date: 2026-11-02

## Problem Statement

用户要求「3分钟后把公司的灯全关了」，新后端持有两个候选集共156个照明成员，却接受只有2条动作、标为「全楼照明关闭」的待确认提案。这不是UI折叠或缺少设备目录，而是业务目标表达、集合解析与完整性校验没有形成端到端保证。已有工具回调、卡片和局部测试通过，不能证明原Runtime的业务语义已被迁移。

原Runtime是用户认可的业务对照；Java承担业务、Node提供基础Agent能力的方向不变。现有实现和修复保留，缺口按业务语义补齐，不将业务搬回Node。

## Solution

让Java维护者在同一处定义和维护Business Agent Definition及真实业务规则。用户表达范围、排除、动作、阶段和只读期间，由Java核验、展开为完整Business Fact，再交付原有卡片；模型不承担大集合清点、权限判断或业务完整性保证。Node继续运行Pi，仅解释通用运行协议，支持流、取消、预算、上下文及声明式停止/恢复指令。

## User Stories

1. 作为公司用户，我希望「全部照明」覆盖当前授权的完整照明范围，而不是模型列出的两个样本。
2. 作为用户，我希望卡片标签、目标数量、展开明细和实际保存成员一致，避免「全楼」只包含局部设备。
3. 作为用户，我希望服务端区分全范围与精确选择，点名两台时不能自动扩成全公司。
4. 作为用户，我希望明确排除的地点成为经核验的真实子集，不能忽略或用模糊匹配猜测。
5. 作为用户，我希望不同阶段各自保留范围与动作，不把两阶段成员合并或丢掉某类设备。
6. 作为用户，我希望未来目标保留当前已满足的设备，不能把即时操作的过滤规则用于未来任务。
7. 作为用户，我希望全授权只读、报表和条件检查不受模型展示窗口或50条动作数组上限影响。
8. 作为用户，我希望省略设备列表不被擅自解释为全部，缺少必要范围或频率时得到准确澄清。
9. 作为用户，我希望能耗统计、对比、报告和模拟补数解释遵守原业务口径，不以模型计算或猜测代替事实。
10. 作为用户，我希望告警、环境、报告、任务引用保留对象身份和期间，不能按标题猜测或串用来源。
11. 作为用户，我希望重复失败不会无限循环，取得新证据后仍可继续合法恢复，不无故整体终止。
12. 作为用户，我希望确定提案后停止新增冲突操作，收尾仍记得已有范围、结果和待确认状态。
13. 作为维护者，我希望新增物联业务、修改prompt、schema、范围或结果投影只修改Java，不要求修改Node源码/产物。
14. 作为维护者，我希望通用引擎修复不包含照明、能耗等领域分支，Java也不复制Pi的上下文压缩和模型循环。
15. 作为验收人员，我希望已知失败原话在真实开发者工具中修复、有匹配构建截图，而不是只增加通过测试数量。
16. 作为集成人，我希望获得完整可重建版本和明确来源，不将尚在推进的会话/缓存改动或临时拼装包当最终基线。

## Implementation Decisions

- 继续执行既有ADR：Java拥有业务prompt、工具名称/schema/描述、范围解析、权限、参数与完整性校验、提案/任务/报告事实、领域恢复决策和小程序事件；Node拥有Pi执行、模型通信、流、取消、预算、上下文压缩及通用协议适配。会话MySQL迁移由另一线程负责。
- 原Runtime只作为单向语义对照，不要求Java/TypeScript逐字一致、工具数量相同或保留已废弃别名。每项有意差异须给出业务等价依据，不以「重构」解释功能减少。
- 全授权、范围/排除和精确选择是不同目标类型。Java以当前身份、来源、会话绑定解析，保存固定成员及绑定；未来新设备不自动加入。全范围展开不受模型显示窗口限制；真实成员不完整时失败或澄清，不静默缩小。
- 参数合法、设备有权访问、范围目标完整是三层不同校验，提案与确认均须保持对应不变量；不通过扩大授权范围或自动补齐精确选择来修复缺失。
- 将原Runtime启用工具、prompt规则、上下文注入、范围/引用、停止/恢复、公开事件列入语义映射。现有深模块与公开入口优先复用；不为各工具复制第二套编排。
- 领域恢复与目标/提案决策在Java；Node只执行与业务无关的预算、调用状态、停止或收尾指令。若现有Tool Bridge不足，版本化扩展通用数据契约并覆盖全部调用方；禁止Node按物联工具名、设备种类或业务字段分支。
- 关闭票据需要源码、实际运行版本和证据一致。领域修复可先独立推进，最终集成需可重建完整产物，不继续以临时叠加运行包作为交付。

## Testing Decisions

- 最高业务验证面仍是现有真实微信前端和Java公开业务入口，Tool Bridge是引擎协作验证面；不另建验收后台或新登录体系。
- 为已知范围缩小缺陷建立消费者反例：完整固定集合超出50条时，全范围动作与该集合一一对应；精确选择不扩张；成员不足、排除冲突或跨身份不得形成误导提案。156是本次观察快照，不作为未来账号的固定默认台数。
- 使用已有行为/契约惯例覆盖边界、权限、状态、错误、重试与副作用去重；不测试源码字符串、wiring、mock回声或精确prompt措辞，不因实现不匹配而改写业务预期。
- 对真实原话走修复后同一前端路径并截图，停在待确认；不为证明用户已报告的问题重复下发或创建任务。
- 循环/恢复使用隔离引擎协议与故障注入验证，并至少关联一个真实前端结果；工程证据不充作业务验收。
- 语义规则需全量映射，但不要求重新遍历全部卡片或全部说明书UI。总体验收仍采用此前约20条、数量与选择不严格的代表口径；本次增加已知缺陷的针对性证据，不新增全卡片门禁。

## Out of Scope

- 改变Java/Node分工、把物联prompt或工具实现搬回Node、纯Java重写Pi。
- 接管、回滚或重新设计另一线程的Pi Session MySQL迁移和缓存支线。
- 修改、运行或切换生产Runtime，生产设备下发、任务创建、通知和配置写入。
- 全卡片遍历、全部说明书UI强制全过、无关视觉重设计和新平台化抽象。
- 以缩小设备/时间范围、扩大授权、吞错、模型补算、模拟卡片或假报告凑验收。
